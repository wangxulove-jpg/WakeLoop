# 鸿蒙专注计时 App —— 开发前调查报告

> 目标：将 Focus-main（macOS）与 random-reminder-main（Web）两个开源专注应用的核心功能移植为 HarmonyOS 本地应用（个人自用），并调查"通过手环心率检测/维持专注状态"的技术可行性。
> 日期：2026-09-07

---

## 1. 两个开源应用的功能分析

### 1.1 Focus-main（macOS / SwiftUI）

| 功能 | 说明 |
| --- | --- |
| 专注计时循环 | 默认 **90 分钟专注 + 20 分钟休息**（BRAC 生理节律），自动进入下一轮 |
| 随机提示音 | 专注期间每 **2~5 分钟（默认3-5分钟）随机间隔**播放提示音，用于"唤醒"注意力 |
| 微休息 | 提示音后进入 **10 秒微休息**（视觉提示），然后继续专注 |
| 黑屏强制休息 | 休息阶段可开启全屏深绿色覆盖窗口，强制用户离开屏幕 |
| 媒体控制 | 休息时自动暂停/静音媒体播放 |
| 统计 | 按日/周/月/年聚合：专注总次数、总时长、平均时长、最长会话、连续天数；柱状图展示 |
| 设置 | 专注/休息时长、提示音开关与随机间隔范围、微休息时长、黑屏开关、媒体静音开关、自定义提示音 |
| 数据模型 | FocusSession：开始时间 + 时长，本地 JSON/UserDefaults 持久化，无后端 |

### 1.2 random-reminder-main（Vue 3 / Web）

与 Focus-main 同源思路（应该就是其 Web 版原型）：

- 随机提示音（默认 2–5 分钟间隔）保持专注；
- 90 分钟专注 + 20 分钟休息循环，专注结束自动进休息、休息结束自动开下一轮；
- 微休息 10 秒；多种提示音可选；
- localStorage 持久化全部状态（含刷新/切后台恢复计时状态）；
- 无后端，纯前端。

**结论：两 App 共享同一套方法论 —— "BRAC 90/20 循环 + 随机提示音 + 微休息"。鸿蒙版 MVP 只需实现这套核心循环 + 本地统计。**

## 2. 鸿蒙版 MVP 功能范围（第一阶段，不依赖心率）

### 2.1 页面（对齐 Focus-main 的布局）

- **主页面**：
  - 顶部：统计入口、设置入口
  - 模式标题（专注 / 休息）、今日已完成周期数
  - 圆形进度环 + 中央倒计时（mm:ss）
  - 开始/暂停、重置按钮
- **设置页**：专注时长、休息时长、提示音开关、随机间隔最小/最大值、微休息时长、提示音选择
- **统计页**：日/周/月切换、总次数、总时长、平均时长、最长会话、连续天数、柱状图

### 2.2 核心逻辑（TimerManager 对等物）

- 状态机：`idle → focusing → (随机提示音+微休息循环) → breaking → focusing → ...`
- 随机提示音：在 [min, max] 区间内随机取下一次间隔；
- 微休息倒计时（10s）；
- 本地持久化：会话记录 + 设置（Preferences 存设置，会话记录用 RelationalStore 或 JSON 文件，个人量级都够用，建议 RelationalStore 便于统计查询）。

### 2.3 鸿蒙特有的关键技术点（调研结论）

| 问题 | 结论 |
| --- | --- |
| 退后台计时被冻结 | 应用退后台会被挂起。方案：**reminderAgentManager（系统提醒代理）** 注册倒计时提醒（专注结束/休息结束）；随机提示音若要在后台响，需**长时任务（backgroundTaskManager）+ 音频播放**保活（random-reminder 的"后台模式"即此思路）。MVP 先做前台计时 + reminderAgent 兜底，够个人使用 |
| 声音资源 | Focus-main 的 mp3/wav 资源可直接复用（放 rawfile，用 AVPlayer 播放） |
| UI 基线 | 遵循《鸿蒙App开发指南.md》：沉浸式 + 安全区避让、深浅色资源限定词、Navigation 路由、统一返回图标 |
| 黑屏强制休息 | 手机端没有 macOS 式全屏遮挡窗口；等价物是**全屏页面 + 亮屏常亮（window.setWindowKeepScreenOn）**，或干脆只做提醒。MVP 简化为"休息提醒 + 常亮休息页"，不做强制锁定 |
| 媒体控制 | 无跨应用媒体控制 API（AVSession 只管自己会话），放弃此功能 |

## 3. 手环心率检测专注状态 —— 技术调查

### 3.1 科学依据：心率/HRV 与专注的关系

- **神经内脏整合模型（Thayer & Lane）**：调节心跳的自主神经回路与调节注意/执行功能的前额叶回路是同一套。HRV（心率变异性）是前额叶"脑力状态"的实时窗口。
- 实证结论（2022 *Psychophysiology* meta 分析等）：
  - **HRV 高 ↔ 持续注意力更好、抗干扰更强**（抑制无关信息能力）；
  - **HRV 低 ↔ 认知负荷高、压力/疲劳累积**，表现为注意力涣散、冲动控制下降；
  - **心率相对个人基线升高 + 持续** → 交感神经激活，对应紧张/焦虑/分心状态。
- 华为手环生态里有一个现成的红利：**华为运动健康 App 本身基于 HRV 计算"压力"得分**，并开放了"压力"和"心率变异性"数据类型（基础数据等级）。

### 3.2 心率数据获取路径（HarmonyOS 手机 App 端）

| 路径 | 原理 | 实时性 | 个人可行性 | 结论 |
| --- | --- | --- | --- | --- |
| **A. Health Service Kit（运动健康服务）** | 手机 App 读华为运动健康 App 汇聚的手环数据（官方唯一第三方通道） | **小时级**（依赖蓝牙连接/后台保活，官方明确不保证实时） | 基础数据（心率、HRV、压力、情绪）**个人开发者可申请**；需提交材料人工审核约 10–15 个工作日；测试权限限 100 用户（自用无影响）；正式权限需上架应用市场 | **首选，但先按"复盘用"设计** |
| B. @ohos.sensor（SensorId.HEART_RATE） | 读设备自身心率传感器 | 秒级 | 手机无 PPG 硬件，**手机端无数据**；仅适用于手表/手环端应用 | 仅当给华为手表开发穿戴端 App 时可用，排除 |
| C. BLE 直连标准心率服务（0x180D） | GATT 客户端订阅 Heart Rate Measurement | 秒级 | API 齐全（@ohos.ble）；但**华为手环与运动健康绑定后不开放标准 BLE 心率服务**（协议私有）；心率带/部分其他品牌手环支持 | 取决于设备，**华为手环不可行** |
| D. Health Industry SDK | 行业穿戴设备开放能力 | 实时（约 1s 上报） | 面向行业合作方，需申请服务证书 | 个人不可行，排除 |

### 3.3 关键限制与影响

1. **Health Service Kit 的"小时级"及时性**：专注会话进行中拿不到秒级心率流。意味着：
   - ❌ 不能做"实时监测心率 → 即时判断走神 → 立刻干预"；
   - ✅ 可以做"**会话后复盘**"：把专注会话时间段与该时段心率/HRV/压力曲线叠加，长期观察"什么状态的专注质量高"；
   - ✅ 长期数据可建立**个人静息心率基线**，用于第二天的状态预判（如晨间静息心率偏高 → 建议缩短单轮专注时长）。
2. 若未来确需实时心率闭环，现实路径是换设备（支持标准 BLE 0x180D 的心率带/手环）或做手表端应用，成本明显上升。

### 3.4 基于心率/HRV 的专注状态推断（会话复盘方案设计）

数据可得性决定算法只能用"粗粒度指标"（这也符合个人项目不过度工程的原则）：

- **基线（Baseline）**：滚动 7 天静息心率均值 + 华为"压力"得分基线；
- **会话指标**：
  - 会话时段平均心率 vs 基线的偏差 ΔHR；
  - 华为 HRV/压力得分在会话前后的变化；
- **推断规则（初版，纯启发式）**：
  - ΔHR ≈ 0 且压力分平稳 → "平静专注"（目标状态）；
  - ΔHR 持续偏高 + 压力分上升 → "紧张/高唤醒"，统计上这类会话的完成率如何，由数据说话；
  - HRV（压力分）持续走低跨多个会话 → 疲劳累积信号，建议缩短下一轮专注或提前休息。
- **验证方式（观测优先）**：第一阶段只做"记录 + 图表叠加 + 人工观察相关性"，不做自动干预闭环；等积累了个人数据后，再决定是否加"智能提示"。

### 3.5 心率功能的分期引入

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| P0 | 纯本地专注计时 App（第 2 节 MVP） | 无 |
| P1 | Health Service Kit 申请 + 集成：读"当日/历史心率、HRV、压力"采样数据，在统计页叠加展示 | 审核通过（10–15 工作日，可与 P0 并行申请） |
| P2 | 专注状态复盘：基线 + 会话相关性分析 | P1 数据积累 |
| P3（可选） | 实时闭环：更换支持标准 BLE 心率的设备或做手表端 | 视需求，默认不做 |

## 4. 风险与决策点

| 风险/决策 | 说明 | 缓解 |
| --- | --- | --- |
| Health Service Kit 个人审核被驳回 | 常见驳回原因：权限说明缺失、应用未上架（针对正式权限）、材料不全 | 按官方"申请被驳回常见问题"清单准备隐私政策与权限用途说明；测试权限阶段不要求上架 |
| ~~手环型号未确认~~ | **已确认：华为手环 9**。走路径 A（Health Service Kit），路径 C（标准 BLE）对华为手环不可行，正式排除 | 手环 9 搭载 TruSeen™5.5（全天连续心率）、全天压力监测（基于 HRV）、TruSleep™4.0（睡眠心率/静息心率）——恰好覆盖"专注复盘"所需的全部数据类型 |
| 后台计时不可靠 | 鸿蒙后台挂起机制 | 前台使用为主 + reminderAgentManager 系统提醒兜底；必要时音频长时任务保活 |
| 数据及时性不达预期 | 官方明确不保证小时级及时性（蓝牙断连/运动健康未保活） | 功能定位为"复盘参考"而非精确监测，UI 上标注数据时间；手环 9 常规使用续航 9 天（心率常开），可保持全天佩戴，数据连续性有保障 |

## 5. 建议实施路线（PoC 分段、独立可验证、可回滚）

1. **PoC-1：计时内核**（无 UI 打磨）——TimerManager 状态机 + 前台倒计时 + 提示音播放 + 单元测试。验证：模拟器跑通 90/20 缩短版循环。
2. **PoC-2：MVP App** —— 主页/设置/统计三页（对齐 Focus-main 布局）+ Preferences/RelationalStore 持久化 + reminderAgent 后台兜底。验证：真机后台切回计时正确、提醒可达。
3. **PoC-3：健康数据接入**（与 PoC-2 并行申请权限）—— Health Service Kit 读心率/HRV/压力，先做成独立 demo 页验证数据可见性。
4. **PoC-4：专注-心率复盘** —— 统计页叠加心率曲线 + 基线计算。

技术选型对齐个人基线：ArkTS/ArkUI 单 HAP、零三方依赖（音频用系统 AVPlayer、数据用系统存储、提醒用 reminderAgentManager），UI 遵循《鸿蒙App开发指南.md》全部基线约定。
